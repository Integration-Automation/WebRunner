## U-20261001-02 · 2026-10-01 · MCP server: UTF-8 stdio, silent notifications, isError for tool failures · #change #mcp

- **What**: first stage of `progress.md` #21, the MCP server's protocol bugs (`je_web_runner/mcp_server/`).
  - stdio: `serve_stdio()` read and wrote with the console code page and CRLF line ends.   - A JSON array (batch) was expanded into separate replies; it is now rejected with one `-32600` error, as batching was removed in MCP 2025-06-18. A non-object message also gets `-32600` instead of silence.
- **Executor**: `execute_action()` now delegates to `collect_action_results(action_list) -> (record, failed)`, which does the same work without printing. `execute_action()`'s output and return value are unchanged.

## U-20261001-33 · 2026-10-01 · Impact index cache: parse only the action files that changed · #done #performance #impact-analysis

- **What**: `progress.md` #16. `impact_analysis.build_index(directory, glob, cache_path=None)` keeps each file's names (commands, locators, URLs, templates) in a JSON cache, keyed by the path relative to the tree.
  - A file is reused when its modification time and size match. When they differ it is read and hashed, and reused if its SHA-256 matches, which is the fresh-checkout case where every time changes. Otherwise it is parsed again.
  - A file that is not an action list is remembered as skipped. Deleted files leave the cache. A cache for another directory, glob or cache version is ignored, and so is an unreadable one (with a warning). The cache is rewritten only when something changed.
  - `build_index` also stats each file once instead of twice (`is_file()` then `stat()`); each stat costs tens of microseconds on Windows.
- **Measured** (3000 or 1000 synthetic files of 30 actions, warm, median of 5, Windows):

  | | 1000 files | 3000 files |
  | --- | --- | --- |
  | before | 179 ms | 601 ms |
  | uncached now | 159 ms | 510 ms |
  | cached | 44 ms | 138 ms |
  | cached, every modification time changed | 158 ms | 457 ms |

  Reading and hashing cost about what parsing does, so the hash check saves little. The cache's gain is local reruns and CI runs that restore the tree with its times. The first read of freshly written files was far slower (6.7 s for 1000), mostly the OS scanning new files, which no cache avoids.
